# 分析流水线性能与质量计划（P4）

目标：单曲分析从 4.7–6.0 s 降到 2–3 s，同时提升音质保真度。

## 现状基线（真机 Pixel，0.72.0）

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| fetch | 0.1–1.0 s | Range 三窗或整段下载 |
| decode | 1.9–4.3 s | 16 kHz，三段各 30 s，**串行** |
| dsp | 0.4 s | FFT 1024 点 |
| clap | 1.3–1.8 s | 三窗，串行 Run |
| 合计 | 4.7–6.0 s | |

## 已识别的质量损失

- CLAP 训练于 48 kHz，但当前输入是「16 kHz 解码 → 上采样到 48 kHz」，8–20 kHz 全为空；
- 30 s 窗解码后只用中间 10 s 喂 CLAP，其余用于 DSP。

## 阶段

### S1 解码并行化（已实现，待实测）
- `decodeParts` 三段由串行改并行（3 线程）；
- 预期 decode → 1.5–1.7 s，单曲 → 3.5–4.5 s。

### S2 真实 48 kHz（已实现，待实测）
- 新增 48 kHz 解码路径供 CLAP 使用；DSP 仍用 16 kHz（抽取或独立解码）；
- 每窗只解 20 s（CLAP 取中 10 s，DSP 用 20 s 统计）；
- 预期解码量不变，质量提升。

### S3 CLAP 并行推理
- 三窗并发 `Session.run`（ORT Run 线程安全）；
- 预期 CLAP → 0.6–0.8 s。

### S4 重试 NNAPI（fp16 模型）
- fp16 对 NNAPI 更友好；若成功单窗 0.3 s。

### S5 DSP 频率分辨率
- 48 kHz 下 FFT 提到 2048 点，保住 15 Hz/bin 分辨率。

### S6 验证与发布
- 同一批曲目对比「新流程 vs 旧流程」的 embedding 余弦（应 ≥0.99 且更稳定）；
- 单曲耗时分布 P50/P95；
- 发版并记录到 CHANGELOG。

## 验收标准

| 项 | 目标 |
| --- | --- |
| 单曲耗时 P50 | ≤3.0 s |
| "安静"类曲目embedding稳定性 | 新旧余弦 ≥0.98 |
| 崩溃 | 0 |


## 进度（2026-11-25）

- S1 已完成：`decodeParts` 三段并发解码；
- S2 已完成：`decodeWhole` 输出 48 kHz；DSP 改用 3:1 抽取后的 16 kHz；CLAP 直接吃 48 kHz，不再上采样；
- 待实测：需要在设备上重新登录后跑一轮，对比 `timing` 日志与 embedding 稳定性。


## 实测结果（2026-11-25，Pixel，debug 包）

| 指标 | 基线 0.72.0 | S1 并行解码 | S2+S3 |
| --- | --- | --- | --- |
| fetch | 0.1–1.0 s | 0.4–0.7 s | 0.2–1.1 s |
| decode | 1.9–4.3 s | 1.3–2.0 s | **1.75–2.0 s**（采样点 ×3 后仍持平） |
| dsp | 0.40 s | 0.40 s | 0.41–0.45 s |
| clap | 1.3–1.8 s | 1.8 s | **1.13–1.20 s** |
| **total** | **4.7–6.0 s** | 4.1–4.7 s | **3.57–4.49 s** |

- S2 使解码量变为 3 倍，但 S1 的并行解码吸收了这个成本，decode 仍保持在 ~1.8 s；
- S3 使 CLAP 从 ~1.8 s 降到 ~1.15 s（三窗并行）；
- 净收益：单曲总耗时下降约 25%，且 CLAP 现在使用真实 48 kHz 音频（音质提升）。


## S4 结论（NNAPI，2026-11-26）

- 在 fp16 模型上重试 NNAPI（不强制 CPU_DISABLED），CLAP 耗时 **1.62–1.89 s**，与 CPU EP（约 1.69 s）持平，无收益；
- 同时观测到 decode/dsp 波动（1.5–2.7 s / 0.56–0.83 s），与设备并发负载有关；
- **决定：不启用 NNAPI**，保持 CPU → XNNPACK 的回退顺序（CPU 优先保证精度）。

## S5 结论（DSP FFT）

- DSP 仍在 16 kHz 上运行（48 kHz 代码设为 3:1 抽取），FFT 1024 点对应 **15.6 Hz/bin**，与改动前一致；
- 因此无需把 FFT 提到 2048，S5 取消。

## 真正的速度—精度权衡

| 组合 | CLAP 耗时 | 精度（对比 fp32 参考） |
| --- | --- | --- |
| fp32 + XNNPACK | ~0.45 s/窗（三窗 1.1–1.2 s） | 1.000 |
| **fp16 + CPU**（当前） | ~1.7 s | **0.99998** |
| fp16 + XNNPACK | ~1.56 s | **0.380（失真）** |
| fp16 + NNAPI | 1.62–1.89 s | 未单独测 |

结论：fp16 权重在 XNNPACK 上会以 fp16 累加导致失真，CPU EP 用 fp32 累加才正确。
若追求速度，唯一无损方案是回到 fp32 模型（APK 回到 278 MB）。
