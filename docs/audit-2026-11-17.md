## 优先级说明

- **P1**：影响体验/正确性，建议尽快处理

## P1 · 高优先级

### 1. ✅ UI 线程同步像素扫描 → 偶发 40~110ms 长帧（性能）
- **现象**：7 分钟模拟中记录到 **25 次 `slow frame`（>30ms）**，最长 **109ms**；其中一次持续约 3 秒、UI 线程 CPU 冲到 **80~87%**。
- **影响范围**：滑动/切歌/封面到达时出现可感知卡顿。
- **触发/复现**：切歌后封面批量到达；`pump_remote` 每帧最多 `poll_n(6)` 条消息，`Msg::Cover` 落在 UI 线程 `remember_cover` → `ink_lum`（两次 `ink_score` 逐像素扫描封面图）；若服务端返回大于 400px 的原图（Navidrome 对 `size=` 参数可能不缩放），单张扫描即数十毫秒，多张同帧到达即叠成长帧。
- **可能原因**：`ink_lum`/`tint_of` 属于像素级重活，却在 UI 线程执行；`tint_of` 虽在 worker 线程，`ink_lum` 却在 `remember_cover`（UI）。
- **建议**：把 `ink_lum` 下沉到 `lumen-art` worker 线程，随 `Msg::Cover` 一起把 `(tint, ink_sq, ink_wide)` 算好送回来，UI 只做纹理上传；并对 `poll_n` 的 Cover 消息做每帧限量（例如 2 条）。

### 2. ✅ 缓存 LRU 的 O(n) 文件读取 + 同步落盘（性能）
- **现象**：模拟中切歌触发预取 2 首后，一次淘汰风暴 **删了 12 个文件、释放 281MB**。
- **影响范围**：缓存较大时，切歌/预取/缓存命中都可能卡顿。
- **触发/复现**：`cache::trim_pool` 在**遍历文件的循环内部**对每个文件调用 `load_lru(dir)`（`src/cache.rs:133`），缓存几百个文件时等于几百次磁盘读+JSON 解析；`cache::touch` 每次命中/预取都 `load_lru + save_lru` 同步落盘，其中 `has_cached` 路径跑在 UI 线程（`play_track_at` 的缓存命中分支）。
- **可能原因**：`load_lru` 未提升到循环外；`touch` 无内存缓存、无延迟批量落盘。
- **建议**：`trim_pool` 开头读一次 `load_lru` 复用；`touch` 改为内存 HashMap + 定期（或退出时）一次性落盘。

### 3. ✅ 专辑页迷你播放条丢失（UI 回归，正确性）
- **现象**：截图确认专辑页底部是**空的黑色条带**，但 `album_layout` 预留了 `bar_h` 空间、`album_input` 注册了 `bar_input` 点击区。
- **影响范围**：专辑页底部约 66pt 区域是「不可见的可点击区」——点它会切播放/暂停或跳播放页，用户却看不到任何控件。
- **触发/复现**：进入任意有曲目的专辑页，看底部。
- **可能原因**：`draw_album` 缺少 `draw_bar` 调用（`draw_home` 有、`draw_album` 没有），疑为上次重构误删。
- **建议**：在 `draw_album` 末尾恢复 `self.draw_bar(p, screen, lay_bar(self, screen))`。

## P2 · 中优先级

### 4. ✅ `audio stall` 检测器切歌时误报（正确性/日志噪音）
- **现象**：模拟中切歌瞬间连发 **5 条 `audio stall: 0.00s in 0.15~0.17s (pos 2488.9)`**，而随后正常出声。
- **影响范围**：日志噪音，掩盖真实欠载信号。
- **触发/复现**：切到一张长专辑（31 首）靠后的曲目，在流打开（~780ms）期间触发。
- **可能原因**：检测器的「每首开头 2 秒保护」在切歌缓冲窗口内未正确生效（`pos_probe` 未随切歌重置 / 曲目索引与 `pos_secs` 冻结期间不一致）。
- **建议**：切歌时显式重置 `pos_probe`；引入「缓冲中」状态（引擎未报位置前不判定）。

### 5. ✅ 切歌起播延迟 ~200~800ms（体验）
- **现象**：`stream[0] playing` 首轮 483~784ms，热身后 ~200ms。
- **影响范围**：点曲目到出声的等待感。
- **触发/复现**：冷启动后第一次切歌。
- **可能原因**：readahead 需先 Range 探测（~40ms）+ 下满第一块 1MB（~300~400ms）才开始解码。
- **建议**：探测与首块并行；或解码器边下边解（对首块用流式），后续块仍走预读。

### 6. ✅ 封面「视线过滤」整套逻辑是死代码（架构/内存）
- **现象**：`Remote::wants`（`Mutex<HashSet<usize>>`）**只被 `set_wants` 写、从未被读**。
- **影响范围**：`want_set` / `set_wants` / `last_wants` 每帧计算+通知全部空转；art 线程仍把 120 张封面全部解码成 `ColorImage` 送进 channel（约 76MB 数据流 + 解码 CPU）。
- **触发/复现**：无，静态可证（`grep -rn "wants" src/remote.rs`）。
- **建议**：要么在 art worker 里真正按 `wants` 跳过非视线封面（只下载文件不解码），要么删掉这套，避免「看起来在做优化」的误导。

### 7. ✅ 缓存 key 不一致 + `fetch_song` 死代码（正确性）
- **现象**：`cached_path()` 固定 `{id}.mp3`，而 `fetch_song()` 按 `{id}.{suffix}` 落盘；`fetch_song` 本身**从未被调用**。
- **影响范围**：若启用 `fetch_song`，同一首歌可能被下两份（`.mp3` 与 `.flac`）。
- **建议**：删除 `fetch_song`，统一用 `cached_path`；或统一缓存 key。

### 8. ✅ 死代码清理（可维护性）
- `make_metal`（旧 CD 设计）、`Playlist`/`playlists`（UI 从不渲染）、`cache_dir2`（与 `cache_dir` 重复）、`fetch_song`、`subsonic::AlbumList.album_list_old` 字段等。
- `model.rs` 顶部注释「现在全是假数据」已过时（`Library::demo()` 现在只是离线兜底）。

### 9. ✅ 歌词面板底部被手势条遮挡（布局）
- **现象**：截图确认最后一行歌词被系统手势白条裁掉。
- **建议**：`playing_layout` 右栏 `ly_bottom` 再上移，纳入 `bar_bottom()`。

### 10. ✅ `step_scroll` 与 `step_inertia` 逻辑重复（可维护性）
- `step_scroll`（首页）与 `step_inertia`（列表）是同一套物理的内联复制。
- **建议**：首页也改成 `step_inertia(&mut self.scroll, &mut self.scroll_vel, self.scroll_max, dt, self.scrolling)`。

## P3 · 低优先级 / 技术债

### 11. ⚠️ 安全与配置（salt 已随机化、补 12 个单测、删未用依赖；密码明文存储 / https-TLS 未做）
- `subsonic::auth()` 用 **`process::id()` 当 salt**（可预测，弱化 `md5(password+salt)` 令牌的抗离线破解能力）。
- 密码**明文**写入 `settings.json`（`Settings::save`）。
- `normalize()` 缺协议时默认补 `http://`；`AndroidManifest` 全局 `usesCleartextTraffic="true"`。
- `ureq` 以 `default-features=false` 引入、**未启用 TLS**——用户若把 Navidrome 放在 https 反向代理后，将无法连接。
- 风险等级：个人局域网应用，风险低，但应在文档中显式说明并后续改进（随机 salt、系统凭据存储、按需 TLS）。

### 12. ⚠️ 测试覆盖极薄 + 无 CI（单测 2→12；CI 仍未加）
- 仅 **2 个单测**（都在 `parse_lrc`）；`Lyrics::index_at`、`parse_stamp`、`uv_cover`、`hue_rgb`/`ink_score`、`fmt_time`、`Settings::normalize`、`cache::trim/touch`、`step_inertia`、`urlencode` 等纯函数全部无测试。
- 无 `.github/workflows`。
- **建议**：给纯几何/解析/缓存逻辑补单测，加一个最小 CI（`cargo test` + `cargo clippy`）。

### 13. ⚠️ 静态分析：`cargo clippy` 14→9 个警告
- `album_list_old` 未读、`Timeline` 未 derive `Default`、`contains()` 代替 `iter().any()`、8 参函数、`io::Error::other`、复杂类型未起别名等。

### 14. 构建与发布
- release 构建**无签名配置**（`isMinifyEnabled=false`、无 `signingConfig`），`.\build.ps1 -Release` 产出的是无法直接安装的未签名包。
- `applicationId="app.lumen.player"`、`android:label="Rust Egui App"` 仍是占位符。
- **无前台服务**：锁屏/退后台后播放会停（仅 `INTERNET`/`ACCESS_NETWORK_STATE` 权限，无 `WAKE_LOCK`/前台服务）——这是已知 TODO，但属于「后台播放」功能缺失。

### 15. 其它
- `safe_area.rs` 用 `OnceLock` 存 JavaVM/Activity 裸指针；`configChanges` 已覆盖旋转/深色/密度，但极端场景（进程内 Activity 重建）指针会失效。
- `current_track_index()` 每帧 O(n) 线性扫描（每帧被调用 ~6 次），`starts` 已有序，可用二分。
- **cached 播放用自由时钟**：`play_file`（缓存命中）路径 `streaming=false`，`tick_audio` 走 `pos_secs += dt`，不读引擎真实位置——seek 或实际时长与元数据不符时进度会漂移；`check_audio_health` 也只监控 `streaming`。

## 实测数据小结（Redmi Pad 横屏，7 分钟连续使用）

| 指标 | 数值 |
| --- | --- |
| 崩溃 / ANR / 解码失败 / 无流可播 | **0** |
| `slow frame`（>30ms） | **25 次**，最长 109ms |
| UI 线程 CPU 峰值 | **87%**（约 3 秒持续 80%+） |
| `motion hitches`（滑动掉帧） | 17 次，avg 16.7ms 稳定，max 24~50ms |
| `audio stall` | 5 条（切歌缓冲期误报，非真实欠载） |
| 起播延迟 | 首轮 483~784ms，热身后 ~200ms |
| 缓存淘汰 | 一次删 12 文件、释放 281MB |

**正面确认**：readahead 预读（1MB/块 × 6 块缓冲）有效吸收了网络抖动（单块 273~434ms 未造成欠载）；字体预热后图集仅占 1%；首页/列表滚动平均帧时间 16.6~18ms，接近 60fps 满帧。
