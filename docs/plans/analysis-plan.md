## Phase 1 · OpenL3 接入

- [x] **P1-1 权重与转换链路（通用版 + 音乐版均已跑通）**
  - 选型修正：MusicFM 仓库权重实测 **1.3 GB**（330M 级），端侧不可用 → 只作离线教师
  - 端侧目标改为 **LAION-CLAP 音频塔（MIT，512 维，int8 ≈40 MB）**
  - 转换器阻塞：`ai-edge-torch` 在本机不可安装（`litert-torch` 依赖的 `litert-converter` 无 Windows/Py3.12 轮子，连独立 venv 也 ResolutionImpossible）
  - **定案（体积无上限）：走 ONNX Runtime 路线，放弃 TFLite 转换**
    - 依赖：`com.microsoft.onnxruntime:onnxruntime-android`（约 20 MB/ABI）
    - 模型：CLAP 音频塔 → ONNX（fp32 ≈150 MB；可 fp16 减半）
    - 前端：48 kHz / 64-mel / 10 s 窗（HTSAT 规格）
    - 推理：每曲 3 窗 → 512 维，mean+std 拼接
    - 存储：float16 BLOB + model_id
    - 收益：绕开 litert-torch 的平台缺失；风险：APK ≈+170 MB、首次加载耗内存
  - venv 内的 tensorflow+onnx2tf 已弃用（不再需要）
  - **端侧冒烟（真机 Pixel 10a）**：dim=1024、norm=21.6；10 s 窗推理 **2.35–2.46 s**（2 线程 2457 ms / 4 线程 2352 ms，基本不随线程数变化 → CPU/内存受限）
  - **int8 动态量化不可用于端侧**：ORT Android 缺 `ConvInteger` 实现 → 必须用 fp32（282 MB）
  - 结论：CLAP 单窗 ≈2.4 s，3 窗 ≈7.2 s 超预算；**建议 1 窗（中段 10 s）**，单曲总耗时 ≈4.6 s（含现有 2.2 s）
  - NNAPI：未成功挂载（无 enabled 日志），已静默回退 CPU
  - 三窗真实耗时：**per=[5532, 3048, 2972] ms，合计 11.55 s**（首窗含预热）
  - QDQ 静态量化（合成校准 24 段）：体积 72.3 MB，但 **fp32 余弦仅 0.308** → 合成校准不可用，必须用真实音乐校准
  - QDQ 真实校准（李志 135 首 mp3，36 段窗）：体积 72.3 MB，余弦 **0.084**
  - QDQ 只量化 MatMul/Gemm：79.3 MB，余弦 **0.076**
  - 动态只量化 MatMul/Gemm：79.2 MB，余弦 **0.058**
  - **结论：ORT 量化工具对该模型不可用（4 种组合全部失败）**；STFT 前置 + HTSAT 对权重扰动极敏感
  - 决策：**放弃量化，使用 fp32 282 MB**；不同窗数下耗时：1 窗 3.0 s / 2 窗 6.0 s / 3 窗 11.5 s
  - **XNNPACK 成功**：`EP=nnapi failed (google-edgetpu 不支持)` → `EP=xnnpack ok`

    - **稳态单窗 0.44–0.50 s**，三窗稳态约 **1.4 s**
    - 较 CPU（3.0 s/窗）提速约 **6×**
  - **结论：保留 3 窗，CLAP 增量 ~1.4–1.5 s/曲**，完全落在预算内

## P0-3 最终耗时（原始流 + 窗口解码，10 个样本）

| 阶段 | 范围 | 说明 |
| --- | --- | --- |
| fetch | 0.5–1.3 s | 原始文件直下，无服务端转码 |
| decode | 1.3–1.8 s | 只解三段窗口 |
| dsp | 0.29 s | 不变 |
| yamnet | 0.040–0.054 s | 不变 |
| **总计** | **2.1–3.4 s** | 原始方案 19–34 s |

全库重算估算：1452 首 × 2.7 s ≈ **65 分钟**（原来 8 小时以上）。

## P0-3 历史分阶段耗时（优化前，真机 2 个样本）

| 阶段 | 样本 1 | 样本 2 | 结论 |
| --- | --- | --- | --- |
| fetch（网络/转码） | 117 ms | 12 305 ms | 波动大，取决于服务器转码缓存 |
| **decode（MediaCodec→PCM）** | **19 046 ms** | **21 061 ms** | **绝对瓶颈，占 56%–95%** |
| dsp | 323 ms | 281 ms | 可接受 |
| yamnet | 80 ms | 56 ms | 极小，XNNPACK 收益有限 |

**结论**：10–30 s/首的耗时几乎全部来自 `decodeSegments` 的逐样本 Kotlin 循环（每样本做声道平均 + 遍历窗口判断），不是模型推理。P0 阶段应先优化解码，而不是 XNNPACK。

**结论**：当前 fuse 的 valence 轴被压缩到 0.19 宽度、97.6% 落在同一象限 —— 情绪"分辨率"几乎为零，标签实际由 arousal 单维决定。这直接验证了 L3（手调映射失真）与 L7（相似度退化），并把 P1/P2 的必要性从"推测"变成"实测"。

### 情绪融合最终方案（softmax 投影）

线性加权 + 缩放会把坐标推到 0/1 两端（146 首实测 p5=0、p50=0、p95=1，arousal p50=1）。
改为：6 个情绪类分数 → softmax(temp=6) → 概率 → 极性投影：

- v = 0.5 + 1.1 × (pHappy + 0.55·pTender − 0.75·pSad − 0.60·pAngry − 0.25·pScary)
- a = 0.18 + 0.75 × (pExciting + 0.85·pAngry + 0.55·pScary) + 0.30·tempoNorm + 0.12·rmsNorm

22 首验证：v 0.496 ± 0.251、a 0.574 ± 0.157，五类标签均出现（Angry 9 / Happy 5 / Sad 3 / Tender 3 / Calm 2）。
